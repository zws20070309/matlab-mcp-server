`mcp_tree_hash` 走 JVM `java.security.MessageDigest`（先实测 `SHA-256("abc")` 与标准值逐位相同才用）；本机 `DigestStream`、`DataHash` 都不可用。哈希按内容算，所以"把同一份字节重写一遍"不会把认证判成 MUTATED（实测 `same_bytes_rewrite_keeps_digest=1`，`edit_changes=1`，`revert_restores=1`）。

## 4. 边界

- 本轮新增/改动的 5 个工具（`suite_run`、`suite_status`、`steps_run`、`longrun_preflight`、`code_refresh`）行为改了，但**注册表描述文本要重启 MCP 进程才刷新到会话面**；本轮全部通过 `evaluate_logged` 的 `codeFile` 通道驱动。
- `MULTI_TREE` 只是把跨树事实说清楚，不替调用者决定：要"单一棵树认证"就得换新 runId 整轮重跑。
- 哈希取前 16 hex（64 bit），用于"变没变"足够，不当作防对抗的指纹；Java 不可用时降级为 FNV 并在前缀打 `fnv`，不假装是 SHA。
- 夹具 `extensions/v10_fixture` 与探针 `extensions/snippets/v11/probe_v11.m` 保留（`test_gamma` 已被探针改为全绿，用于跑通"修复后续跑到 CERTIFIED"这条路径）；注册表回滚备份 `*.bak-v11-*`、`*.bak-v10-*` 保留。

## 5. 一次跨仓库写入与它的两道闸

**事故**：00:05:58(+0800) 一条 `kind=command` 的 `genCounts` 步骤在共享 MATLAB 会话里解析到了 **TEPC 仓库**的同名生成器（`D:\Desktop\网页\仿真\TEPC\shixian\tepc-digital-twin\tools\genCounts.m`），于是写的是它的 `docs/counts.json`（7174 字节，sha256 `55d9cf7c…c5f602`），不是夹具的。该仓库不在版本控制下，没有可回滚的快照；写入内容由它自己的生成器产出，与它自己的树自洽，但**这是一次未经你要求的跨仓库写入**，需要你决定是否复验或还原。

**修了两处（`steps_run.m`）**：
1. `addpath(p, '-begin')` —— 被测仓库必须压过别的路径上的同名函数，`addpath` 追加在后等于没加。
2. `first_resolution` —— 执行命令前按 MATLAB 的方式解析每个 `;=` 段的首标识符（`which`），解析结果落在 `repoRoot` 与 MCP 自身目录之外就**拒绝执行**，并报出它本来会跑的那个文件。

闸自身有过两次误报，都已修并留了回归：
- 拦到 MathWorks 内置 `addpath`（`D:\matlab\toolbox\matlab\general\addpath.m`）：跳过 `matlabroot` 之下的路径——工具箱不是"别人的仓库"。
- 拦到自带 `addpath(X,'-begin'); genCounts` 这种**自己会纠正顺序**的命令：`which` 是在命令执行前问的，所以那时看到的还是旧路径。现在先把命令自带的 `addpath` 段执行掉再解析（steps_run 退出时 `restore_path` 还原会话路径）。

回归（同一批 step，改动后重跑）：
| 场景 | 结果 |
|---|---|
| 裸 `genCounts`（无 addpath） | 仍拒：`the command resolves outside repoRoot (…TEPC…genCounts.m)` `s20260928T161251Z` |
| 配方 `steps_closeout.json` 3 步 | `ALL_OK`，只写 `v10_fixture/docs/counts.json`；TEPC 那个文件的 mtime 仍是 00:05:58，**没被再碰** `s20260928T161136Z` |
| 配方 `steps_final.json` 6 步（json/command/docsync/anchor/test/exists） | `ALL_OK` `s20260928T161221Z` |
| `anchors` 好/坏登记表 + `fresh` 产物 | 好表 `2/2 anchor(s) matched`；坏表 `1 anchor(s) stale: …"MISSING-token-9Z"`；`fresh` 报 `0 source file(s) newer` `s20260928T161425Z` |

**顺手抓到并修掉的注册表谎**：`optsJson` 里写的 `stopOnFail` 一直被解析、**却从未被读**——任何失败都 `break`。现在 `stopOnFail=false` 真的把整表跑完并打 `OK_WITH_%d_SKIPPED_FAILS` + 首条失败原文，默认仍 `ABORTED_AT_k_OF_n`（`s20260928T161426Z`）。这类"描述里有、代码里没有"的选项和前两轮 `warnOnly`、`runId/stepsFile` 是同一族缺陷：**注册表里出现的每个键名都必须能在 `.m` 里 grep 到读取点**。
