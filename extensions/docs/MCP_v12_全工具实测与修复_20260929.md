## 4. 无法修复 / 本轮未复验

**无法修复（在 exe 里，没有源码）**
1. 5 个内置工具与扩展工具**功能重叠**：`check_matlab_code`(单文件) vs `check_code_tree`(整树)、`run_matlab_test_file` vs `run_tests`、`evaluate_matlab_code` vs `evaluate_logged`/`eval_async`、`detect_matlab_toolboxes` vs `env_report`/`resolve_capability`。重叠本身不致命，但**代价可测**：`detect_matlab_toolboxes` 一次调用吐 110 行、每行重复 `版本 25.1 (R2025a)`，约 6.5 KB；同样的信息 `env_report` 一行 `products 110 installed` 就给完。建议：这 5 个内置项在客户端配置里关掉，或至少默认不用 `detect_matlab_toolboxes`。
2. `required` 列了**每一个**形参 ⇒ 所有可选参数都得传空占位。实测代价：`submit_sweep` 要凑 7 个参数才能干活、`sl_sim` 5 个、`session_info` 连只读的 `level` 都必填（我第一次调用直接被客户端校验挡掉）。v12 门禁已不再禁止修它（改成 `required ⊆ order`），但**具体该留哪几个必填要按每个 .m 的 `badArgs` 守卫逐个定**，且改完只有重启才能验；盲改一旦改错，重启后是"工具直接不可用"，比现在更糟 ⇒ 本轮只解锁、不动手。
3. `resolve_capability` 对包命名空间仍失效：它的描述说"用 `which()` 代替 `exist()` 来避开 `H5F` 的假阴性"，实测 `H5F` 仍报 `MISSING / no owning product on this machine`（`which` 对 `+package` 同样返回空，正解是 `meta.package.fromName`）。另外它对 7 个函数各重复一遍 `(ver() exposes no Folder field on this release...)`，约 500 字符纯噪音；`gpuArray` 那行的 toolbox 名是字面量 `"?"`。
4. `sl_sim` 没有 VERDICT 行，而 `sl_build` 有；代数环警告是用**宿主语言**（中文 `找到包含 ... 的代数环`）夹在中间打印的，扫 VERDICT 的调用方会漏掉。（我那个模型确实有代数环：Trapezoidal 离散积分器有直通，`SUM→IXD→G2ZW→SUM` 成环；结果仍准，但这是模型质量问题，工具该在判定里点出来。）
5. `gpu_probe` 与 `gpu_mc` 对同一个量的标注方向相反：`SPEEDUP single gpu/cpu = 0.16x` vs `MEASURED SPEEDUP cpu/gpu = 0.29x`，容易读反。
6. `enable_checkpoint` 的定时器**没有寿命上限**：我 00:48 开的 45 s 周期定时器，到 03:39 仍在写（`checkpoint.mat` mtime 11:40、`checkpoint_history` 里 11:38/11:39/11:40 三份），无人值守跑了近 3 小时、约 240 次快照，只有进程死掉或显式传 `periodSeconds=0` 才停。我已停掉（`checkpoint timer removed`）。建议加"idle N 分钟后自停"。

- `suite_run` + `suite_status` 的认证路径：`suite_run` 被它自己的主机闸**正确拦下**（`[suite_run:hostGate] not starting: 2 MATLAB process(es), 455 MB free`），我没有 `force=true` 硬闯。

### 第二轮里新抓到的第 11 条缺陷（已修 + 已现场复验）

## 15. 又砍掉一处**每次调用**都要付的上下文，以及一条查不到的死路

### 15.1 `resolve_capability` 的输出从 O(n) 降到 O(1)

§13.3 说明了在懒加载下"每轮固定成本只跟工具个数有关"，但还有另一半成本是**工具输出**——它每次调用都进上下文。
`resolve_capability` 原来把一句 86 字符的免责说明**拼在每个命中名字的 `owner` 字符串里**：

```matlab
owner = sprintf('provided by toolbox directory "%s" (ver() exposes no Folder field on this release, so no product-name mapping is claimed)', seg);
```
实测那次 8 个名字的查询里，这句话**重复了 6 遍**（`lhsdesign`/`H5F` 是 MISSING 所以没有）。
现在它只在整次调用里打**一次**、两行：

```
installed products: 110
                               note: ver() exposes no Folder field on this release, so attribution below
                               is by toolbox DIRECTORY, not product name
sim                          AVAILABLE   provided by toolbox directory "simulink"
gpuArray                     AVAILABLE   built-in (no .m file on the path to attribute)
```
顺手修掉 §4.3 里那条 `gpuArray` 的 `toolbox directory "?"`：现在说 **`built-in (no .m file on the path to attribute)`**，
这是实话（它是内建方法，路径行本来就写着 `gpuArray is a built-in method`），不是把一个未知值打印成问号。
节省量随查询规模走：8 个名字省约 380 字符，20 个名字省约 1600 字符——**因为原来是 O(n)，现在是 O(1)**。
复验：`check_code_tree(resolve_capability.m) → error=0`，实况输出如上。

### 15.2 一条死路：exe 里没有"关掉某个工具"的开关

§4.1 建议把 5 个重叠的内置工具关掉，所以我去查了服务端能不能做到。对
`matlab-mcp-server-windows-x64.exe` 做字符串搜索（`disabledTools|enabledTools|toolFilter|excludeTools|hidden|autoApprove`
以及注册表文件名）：只命中 2 处 `hidden`，**没有任何工具过滤键，也没有注册表文件名的明文字符串**；
`reload*`/`refresh*` 的命中全是 MATLAB 自带的内部符号（`refreshPinnerBits`、`reloadpubdaterowsp`、`reloaderInfo`）。
⇒ **服务端没有这个杠杆**，那 5 个内置工具只能从客户端配置层面处理，而那不在 `extensions/` 里、也不是我能改的。
这是"查过、没有"的结论，不是"我没查"的猜测。

### 15.3 我这一轮**两次**用同一种方式把 .m 文件改坏（过程证据，值得记）

`file_op.m`（§10）和 `resolve_capability.m`（本轮）都被我改出过
`错误: 行 NNN 字符向量未正常终止`。两次同一个原因：在 `node -e '...'` 里写 `\\n`，
落到 MATLAB 源码里变成了**真的换行**，把 char 字面量劈成两行。
可靠的写法是 MATLAB 的 `newline` 常量（`file_op.m` 那次就是这么修好的），或者直接用编辑工具而不是脚本拼接。

更值得记的是**第二次修复本身也是错的**：我用两个 `fprintf` 拼一句话、把 `fprintf(newline)` 放在两句之后，
结果渲染成一行、中间夹着 28 个 `%-28s` 补的空格；而且注释写"attribution **above**"，
可这条 note 其实打在**所有条目之前**，应该是 below。
两个错都只有**看真实渲染输出**才发现——看 diff 是完全看不出来的。
⇒ 结论：改完 .m **必须真跑一次看输出**，`checkcode error=0` 和"补丁看起来对"都不构成验证。
（这一轮 `checkcode` 全程 `error=0`，而文件是坏的：`字符向量未正常终止` 是**解析期**错误，
`check_code_tree` 那次是在我修好之后才跑的，所以没抓到中间的坏状态——不能拿它当"改完就安全"的证据。）

### 15.4 我在 §15.1 那个补丁里**又**造了一个新缺陷，靠真跑才发现

把 `gpuArray` 的 `toolbox directory "?"` 改成 `built-in (no .m file on the path to attribute)` 时，
我用 `strcmp(seg,'?')` 当"是内建函数"的判据。**这是错的**：`seg='?'` 只表示
`which()` 给出的路径里**没有 `toolbox`/`extern`/`sys` 段**，也就是"项目/用户目录里的函数"。
后果立刻出现在同一次输出里，自相矛盾：

```
sl_build   AVAILABLE   built-in (no .m file on the path to attribute)
             path: C:/Users/ZWS/matlab-mcp-server/extensions/functions/sl_build.m
```
上一行说"没有 .m 文件"，下一行就把那个 .m 的路径打出来了。凡是不在 MathWorks 工具箱目录下的函数
（**包括这套 MCP 自己的 32 个工具**）都会被误报成"内建"。

改成三分支后自洽了：

```
gpuArray    AVAILABLE  built-in (no .m file on the path to attribute)
              path: gpuArray is a built-in method
sl_build    AVAILABLE  provided by a folder outside any toolbox (C:/Users/ZWS/matlab-mcp-server/extensions/functions)
              path: C:/Users/ZWS/matlab-mcp-server/extensions/functions/sl_build.m
sim         AVAILABLE  provided by toolbox directory "simulink"
```
判据是 `~strcmp(seg,'?')` → 工具箱目录；`exist(w,'file')==2` → 工具箱外的真实文件；否则才是内建。
复验：`check_matlab_code(resolve_capability.m)` 只剩**改动前就有**的那条 info（line 29 循环内变量增长），
我引入的那条 `warning`（关键字与 END 未对齐，因为我两次把缩进写成了 32 空格）已消掉。

**这一节和 §15.3 是同一个教训的两面**：补丁"看起来对"和"跑起来对"是两回事，
而且**第二次的错只有把输出读到底才发现**——如果我只看 `gpuArray` 那一行，就会以为修好了。
⇒ 结论：改一个分类/归属分支后，**每个分支各挑一个样本跑一遍**（那次是：工具箱内 `sim` /
工具箱外 `sl_build` / 真内建 `gpuArray`），不要只验当初报错的那一个。

## 17. 第 18 条：被取消的作业**在磁盘上不留原因**，而 `cancel_job` 手里就有那个原因

翻 `jobs/` 做历史失败归因时发现的。同一个目录里两种作业的留痕完全不同：

```
jobs/job_20260928_211352_92767604/     <- worker 侧失败
  meta.json + run.log + done.json
  done.json = {"status":"failed","message":"精度无效。","identifier":"MATLAB:badprecision_mx",
               "failedAt":"2026-09-28 21:14:59","stackAt":"diag_report_semantics","stackLine":51}

jobs/job_20260929_115730_09195317/     <- 我取消的
  meta.json 只有一个文件，status="cancelled"，没有 done.json、没有 run.log
```
而 `cancel_job` **当时就把原因打印出来了**（`errorId: parallel:job:UserCancellation`），
因为它的代码里 `[after, errId, errMsg] = mcp_job_state(hit)` 已经拿到了这两个值——
**然后只把 `meta.status` 写盘，把 errId/errMsg 扔了**。后果正是 `job_status` 自己描述里承诺的那条失效：
"Works even after the MATLAB session restarted (falls back to on-disk records)" —— 回落到磁盘时**无因可查**。

修法：`cancel_job` 在 `done.json` 不存在时补写一份，字段形状照 worker 的来（`status/identifier/message` + 时间戳 + 来源说明），
这样 `job_status` 现有的解析路径直接就能读。复验：

```
cancelled: job_20260929_123820_11705721 (state queued -> cancelled)
errorId:   parallel:job:UserCancellation
recorded: C:\...\jobs\job_20260929_123820_11705721\done.json
done.json = {"status":"cancelled","identifier":"parallel:job:UserCancellation",
             "message":"The job was cancelled by user \"ZWS\" on machine \"LAPTOP-AM19OQA8\".",
             "cancelledAt":"2026-09-29 12:38:48",
             "note":"written by cancel_job: the worker did not run to completion, so it wrote no record"}
```
（`fwrite(fid, jsonencode(rec))` 不带精度参数——`fwrite(fid, x, 'utf8')` 会抛 `MATLAB:badprecision_mx`，
正是上面那个 worker 侧失败作业的同一个错因。）

### 17.1 同一族里我**没有**修的一半（说明理由）

`jobs/job_20260929_004912_47968453/meta.json` 至今仍写着 `"status":"queued"`，而它其实早就
`failed`（`MATLAB:TooManyOutputs`，`job_status` 从活句柄读得到）。**worker 还没来得及写 done.json 就失败的作业，
磁盘记录会永远停在 queued**：`list_jobs`/`job_status` 只在活句柄还在时说真话，会话一重启就退回"queued"。
要修得让 `job_status`/`list_jobs` 这两个**只读报告工具**在发现终态时回写磁盘——那是给只读工具加写副作用，
属于设计取舍，我没有替你决定，只把证据留在这儿。

### 17.2 更正我上一轮说过的一句话

我说过"`numWorkers=0` 提交后立刻取消，不会让 worker 真起来，所以是零内存代价的验证手段"。
**这句不可靠。** 这次提交后实测 `MATLAB.exe` 从 **2 变成 3**、free 从 1145 掉到 **923 MB**——
排队中的作业**可能已经起了 worker**，取消只是让它退出（取消后 `MATLAB.exe` 回到 2、free 回到 1145 MB）。
在你明确要求"不要把内存跑满"的前提下，这个手段我**只用了一次**、立刻取消、并确认进程数回到基线；
之前那 3 次没观察到多出来的进程，只能说明 worker 在我采样前就退出了，**不等于它没起过**。

## 18. 上下文占用的**准确**账（按真正发出去的字节算，不是按文件大小）

之前 §13.3 用的是"注册表文件字节数"，那个口径不准。`mcp_get` 的**实际返回形状**是
`{name, description, inputSchema, serverName, originalName}` —— 也就是说：

- `signatures` 块（**2752 字符**）**不发**给客户端，它是 exe 内部用来知道怎么调 `.m` 的；
- 每个工具的 `title`（合计 **720 字符**）**也不发**；
- 文件里的缩进空白（**11314 字符**）更不发。

⇒ 注册表文件 30435 字节，但**真正进上下文的只有 15627 字符**。拿文件大小当上下文指标会高估近一倍。

按"真正发出去的载荷"重新实测（32 个扩展工具，77 个参数）：

| | 字符 | ≈tokens | 说明 |
|---|---|---|---|
| **当前会话在付的**（exe 启动时读的是 v11 瘦身前的注册表） | **38786** | **~9697** | 描述占 52.5%、schema 占 41.7%；`Pass "" when not using it - this bridge requires every listed argument to be present` 这句 69 字符的样板**重复 31 次**（~2139 字符） |
| **reload 之后会付的**（磁盘现状） | **15627** | **~3907** | 描述 3833（24.5%）、schema 9639（61.7%）；那句样板只剩 **1 次** |
| **reload 净省** | **−23159** | **−5790** | **−59.7%**，每轮对话都省 |

这是"精简上下文"这条要求的**主要答案**：省下来的量已经在磁盘上，只差 `/mcp reload` 一条命令。

### 18.1 剩下那 15627 里，约九成砍不动（逐项量化）

schema 那 8590 字符的构成：

| 组成 | 字符 | 占比 | 能不能砍 |
|---|---|---|---|
| 参数说明文本 | 2550 | 29.7% | **不该砍**——这是 `optsJson` 有哪些键的唯一文档；砍了等于把我刚修的 #12（`glob` 没人知道）再造一遍 |
| `"description":` 这个 JSON 键 ×77 | 1232 | 14.3% | 协议规定，砍不了 |
| `"type":"string"` ×77 | 1232 | 14.3% | 协议规定，砍不了 |
| 每个工具的 `{type,properties}` 外壳 | 1056 | 12.3% | 协议规定 |
| `additionalProperties:false` ×32 | 928 | 10.8% | **不该砍**——它是"参数名打错就报错"而不是"静默忽略"的唯一保障 |
| `required` 数组（列了全部 77 个参数名） | 812 | 9.5% | 唯一可自由裁量的一块，见 18.2 |
| 参数名本身 ×77 | 780 | 9.1% | 就是形参名，砍不了 |

单个工具最贵的：`file_op` 948、`submit_sweep` 853、`submit_job` 794、`suite_run` 756、`steps_run` 710。
`submit_sweep`/`submit_job` 贵是因为它们有 7 个和 6 个参数，而**每个都在 `required` 里**。

### 18.2 为什么我**没有**去砍 `required`（尽管它同时就是 §4 那条人体工学缺陷）

- 取证能力不够：我从每个 `.m` 里提取"空值会触发 `:badArgs`"的参数当真必填，32 个工具里只有 **8 个**提取到证据
  （`get_variable[name]`、`eval_async[code]`、`evaluate_logged[code]`、`gpu_mc[funPath]`、`file_op[action,target]`、
  `run_tests[testPath]`、`sl_sim[modelPath]`、`sl_build[modelPath,specJson]`），其余 **24 个没有 `badArgs` 守卫可取证**。
- 上限收益很小：`required` 数组总共 812 字符，全砍也只省 ~200 tokens ≈ **reload 后载荷的 1.3%**。
- 风险不对称：砍错一个，reload 之后那个工具**直接调不动**（客户端不再传该参数，而 `.m` 未必有 `nargin` 默认值），
  而且**我当场验不了**——只有 reload 才生效。

⇒ 用 1.3% 的收益换"可能让工具直接不可用且无法当场证伪"，不划算。**我只把门禁解锁**
（v12 已把 `required == order` 放宽为 `required ⊆ order`），逐工具取证留给有 reload 条件时做。

### 18.3 "减少工具个数"这条路：查过了，目前不成立

懒加载下每轮固定开销只有 37 个工具名（~1011 字节），所以减少**个数**是唯一能降每轮成本的杠杆。
最像的合并候选是 `capture_figure` ⊂ `capture_app`——`capture_app` 的注释就写着 `mode='auto'` 用 `exportapp`、
"handles BOTH traditional figures and uifigures on R2025a (verified)"，而且还有 `mode='exportgraphics'` 分支。
**但查代码后发现不等价**：

```
capture_figure.m:43   exportgraphics(fig, outPath, 'Resolution', 150);      <- 钉死 150 dpi
capture_app.m         exportapp(fig, outPath) / exportgraphics(fig, outPath) <- 都不传 Resolution
```
`capture_figure` 唯一不可替代的就是那个 **150 dpi 保证**，现在合并会丢功能，所以我没动它。
要走这条路，正确顺序是先给 `capture_app` 加 dpi 选项、验证等价，再谈删 `capture_figure`——
那是接口设计变更，不该在无法 reload 验证时顺手做。

5 个内置工具在 exe 里，而 exe 中**不存在任何工具过滤键**（§15.2 已按字符串搜过），只能从客户端配置层面处理。

### 18.4 已经落地、**不依赖 reload** 的那部分精简

`resolve_capability` 的输出从 **O(n) 降到 O(1)**（§15.1）：那句 86 字符的免责说明原来拼在**每个**命中名字里
（8 个名字的查询重复 6 次），现在整次调用只打一次。这是**工具输出**侧的精简，改的是 `.m`，**已经生效**。

### 19.2 reload 之后**才看得见**的 3 条新缺陷（第 19~21 条）

瘦身把描述压短的时候，**枚举值和描述文本没保持同步**。这事在 reload 前看不出来——因为实况表面挂的还是旧的长描述。
4 个带 enum 的参数里 **3 个对不上**：

| 工具.参数 | enum 真值 | 描述写的 | 后果 |
|---|---|---|---|
| `capture_app.mode` | `auto,exportapp,exportgraphics,screen` | `"figure" \| "app" \| "auto"` | **照着文档传 `figure`/`app` 会被客户端校验直接拒**；而 3 个真值一个都没提 |
| `get_variable.mode` | `summary,head,csv,json` | `"summary" \| "head" \| "json"` | `csv` 不可发现——而它正是"大数组别打印、写 CSV"的那个出口 |
| `file_op.action` | 14 个 | 11 个 | `hash`/`exists`/`mkdir` 不可发现（我这轮全都用过、都能用） |

挪进**工具级描述**——那里没有竖线，不会被解析器误读。
**这 3 条要再 `/mcp reload` 一次才上面**（enum 本身早就对了、有权威性，错的只是给人看的那句提示）。

### 19.3 门禁升到 v13：把"描述 ↔ enum"也变成机器判据

v12 只查了 enum ↔ **代码**，所以这一族它抓不到。v13 加了第三个方向：**描述里列的值必须与 enum 双向一致**
（描述写了 enum 不收的 → 报"照着文档调会被拒"；enum 收了描述没写的 → 报"不可发现"）。
先跑在**未修**的注册表上取证，它报出 **9 条**（比我人工数的 6 条多，多出的正是 `get_variable.mode` 漏 `csv`
和 `file_op.action` 漏 `hash`/`exists`/`mkdir`）；修完复跑 `tools=32 citedKeys=59 enumValues=94 problems=0 CONTRACT OK`。
`check_registry_v12.js` 已移入 `_archive/registry_backups/`——我上一轮用 `node -e` 拼接改它时
把 JS 字符串转义写坏了（`SyntaxError: missing ) after argument list`），与其在坏文件上继续打补丁，
不如整份重写成 v13。

至此"描述与实现不一致"这一族有了**三个方向**的机器判据：描述↔代码（v11 的引号键名对账）、
enum↔代码（v12）、描述↔enum（v13）。这一族今晚已经第 8 次出现了。
